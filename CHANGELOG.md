## [Unreleased]

### Fixed
- **Bytecode Compilers (Stack VM and Register VM) — Internal Limits Silently Miscompiled Nested Functions**: Both bytecode compilers track failure in a per-compiler `had_error` flag, but a *nested* function body got its own compiler whose flag was never read by the enclosing one. A function that blew an internal limit (more than 255 locals, or — in the register VM — an expression needing more than 250 of the 250 virtual registers) therefore left the outer compiler emitting a closure over half-built bytecode, which the VM then happily ran. The observable result was a wrong answer with no diagnostic and a **success exit code**: a 300-local function that returns `7` printed `null` under both VMs while the AST interpreter and the native C99 backend printed `7`. The register allocator made this worse by returning register 0 on exhaustion — the slot holding the live closure — so the corruption started before the limit was even reported.
  - Nested-function failures now propagate to the enclosing compiler at every site that builds one (function expressions, function statements, and struct/impl methods), aborting the whole compile.
  - Every internal limit now reports a real, located diagnostic naming the function and the limit (e.g. `Too many local variables in function 'f' (limit is 255); split it into smaller functions`) instead of only setting a silent flag. This covers the local, upvalue, register, jump-distance, loop-size, and match-arm-test limits in both compilers.
  - The bytecode cache header version was bumped (v2 → v3) so bytecode cached by an older build — which may have been miscompiled by exactly this bug — is discarded rather than replayed. Without the bump, a cached `.ufc`/`.ufrc` kept producing the silent wrong answer even after the compiler was fixed, because the cache is keyed on the source hash and the source hadn't changed.
- **Lexer — CRLF (Windows) Files Failed to Parse Entirely**: `skip_horizontal_whitespace_and_comments` treated `\r` as ordinary horizontal whitespace and consumed it with `advance()`, which treats a lone `\r` or a `\r\n` pair as one complete line break. The line ending was therefore swallowed before the scanner could emit a `NEWLINE` token, so **every source file saved with Windows line endings failed with `Syntax Error: Expected newline after variable declaration`** — not a line-numbering nuisance but a total parse failure, on files that any Windows editor or a `core.autocrlf` checkout produces by default. Two comment-skipping loops had the matching bug: both tested only for `\n`, so on a CRLF file `advance()` consumed the `\r\n` whole and the loop ran on past the end of the comment into the following line. `\r` is now left for the main scanner (which already handles both terminators), and both comment loops stop at either one. Line and column numbers in diagnostics were already correct and are unchanged.
- **Formatter — Produced Source That No Longer Parsed, and Grew `...` On Every Pass**: three separate defects, each in a construct the round-trip test's four hand-picked files happened not to contain. (a) A single-statement anonymous function was always expanded into an indented block, but a block-bodied lambda cannot be re-parsed inside an argument list, so formatting `assert_throws(function(): error("boom"), "msg")` emitted code that failed with `Syntax Error: Expected ')' after function arguments` — valid input turned into a syntax error. Single-statement bodies now stay inline. (b) An `impl` block nested in a struct body names only the trait, its target being the enclosing struct, but the parser fills in `struct_name` anyway and the formatter emitted the free-standing `impl Trait for Struct:` form, which the parser then rejected inside a struct. (c) A `...rest` pattern in a map destructure was written by the map case *and* by the `UF_PAT_REST` subpattern that prints its own ellipsis, so `...rest` became `......rest` on the first pass and grew by three characters on every pass after that.
- **Native C99 Backend — `sqrt`/`log` Returned `nan` Instead of Raising**: `uf_math_sqrt` and `uf_math_log` called libm directly with no domain check, so `sqrt(-1)` produced `nan` and `log(0)` produced `-inf` where the interpreter and both VMs raise a catchable `DomainError`. A program that reports a clean error in development therefore computed silently with garbage once compiled — the most dangerous direction for a divergence to run. Both now raise the identical error, with the same `err.kind` and message text as `uf_stdlib.c`.
- **Native C99 Backend — `to_number`, `char_at` and `substring` Disagreed With Every Other Backend**: `to_number("12abc")` returned `12` natively (a partial `strtod` parse) versus `null` everywhere else; `char_at` delegated to string indexing, so an out-of-range index **aborted the program** instead of returning `""`; and `substring` clamped a negative index to 0 rather than counting back from the end, so `substring("hello", -1, 3)` gave `"hel"` instead of `""`. All three now mirror `uf_stdlib.c` exactly, including its clamping order.
- **AST Interpreter — Relational Operators Rejected Strings**: `"a" < "b"` raised `Comparison operands must be numbers` in the tree-walking interpreter while the stack VM, register VM and native backend all compared strings lexicographically — and `sort()`'s own default comparison ordered strings on every backend including the interpreter. So the interpreter was the one backend that could not do by hand what its own `sort` did internally. It now uses the same `strcmp` ordering as the other three.
- **Doc Generator — First Documented Declaration Lost Its Docstring**: in any file that opens directly with a documented declaration rather than a separate module docstring, the leading `##` block was consumed as the file's description and the declaration it was attached to rendered with an empty body. The generator computed whether the block was attached to following code and then discarded the answer, assigning `module_doc` unconditionally. A leading block is now treated as the module docstring only when a blank line separates it from what follows.

- **Language Server — Ignored Every Request From a Client That Pretty-Prints JSON**: dispatch matched the literal substring `"method":"initialize"`, so a request written `{ "method": "initialize" }` — the same JSON document, since whitespace around a colon is insignificant — matched no arm at all. The server answered every request with a bare `result: null`, advertised no capabilities, and published no diagnostics, while otherwise appearing to run normally. The method name is now pulled out with the existing whitespace-tolerant extractor and dispatched by exact comparison. Every pre-existing LSP test used compact JSON, which is why this went unseen.
- **`unfish pkg init` Scaffolded a Package That Failed `unfish pkg test` Immediately**: the generated test file imported the testing module as `from "testing" import assert_equal`, but a module name in a from-import is a bare identifier and the quoted form is a syntax error. The very first command a new user runs after `pkg init` therefore failed. The unit test covering `pkg init` checked only that the files existed and that `pkg check` passed; it now runs `uf_pkg_test()` for real.
- **Bundled Stdlib Modules Were Only Importable From the Unfish Source Tree**: `import testing` resolved the bundled module through the working-directory-relative path `src/stdlib/<name>.unfish`, so it worked when run from the repository root and nowhere else — including from a user's own package directory, which is exactly where `unfish pkg test` runs. Bundled modules are now located relative to the executable (`<bin>/../src/stdlib`, `<prefix>/lib/unfish/stdlib`, or a `stdlib` directory beside the binary), with the old working-directory path kept as a final fallback.

- **Register VM — Segfault on an Uncaught Error After a Caught One**: The register VM keeps its own try-handler stack (`vm->handlers`) alongside the runtime's (`rt->try_handlers`); `ROP_PUSH_TRY` pushes onto both. When `regvm_runtime_error` caught an error via the VM's stack directly — the path taken by VM-detected errors such as a stack overflow — it popped only the VM's copy and left the runtime's behind, desynchronising the two stacks. The next uncaught error found that stale runtime handler still live and `longjmp`ed into it, landing in the `setjmp` arm of a `ROP_PUSH_TRY` whose VM handler stack was now empty: it read `vm->handlers[-1]` (confirmed by UBSan) and jumped to the garbage instruction pointer found there, **segfaulting the process** (exit 139) instead of reporting the error. Reproducible from ordinary code — catch a division by zero, then let a second one go uncaught. The error path now pops both stacks together, and the `setjmp` landing site refuses to index an empty handler stack rather than trusting the invariant.
- **Native C99 Backend — Deep Recursion Dumped Core Instead of Raising**: Native binaries recurse on the real C stack with no depth guard at all, so runaway recursion — an infinite recursion, or merely a deep one — crashed the process with a segfault and a core dump, while the AST interpreter and both VMs raise a catchable `StackOverflowError`. Generated functions now call `uf_rt_check_stack()` on entry, which raises the same catchable `StackOverflowError` (same `err.kind`, so `try`/`catch` behaves identically across all four backends) once the stack has grown past a 4 MB budget. The guard measures how far the stack has grown from `main()` rather than counting frames: a counter would need a matching decrement on every exit path, and `uf_throw` `longjmp`s straight out of nested calls without running any epilogue, which would leave such a count permanently skewed. This restores the behaviour `docs/ERROR_MODEL.md` already documents, where `StackOverflowError` is a catchable Tier 2 exception like `DivisionByZero` or `IndexOutOfBounds`.

### Changed
- **Native C99 Runtime — Maps Are Now Actually Hash Maps**: `UfRtMap` carried the shape of a hash table (`entries`, `capacity`, a 75% load factor, growth by doubling) but never hashed anything: every lookup, insert, membership test, and delete scanned the whole table comparing keys with `strcmp`, and insertion took the first free slot. Map-heavy native programs were therefore O(n) per operation and O(n²) overall — the `hash_map_stress` benchmark ran **35x slower natively (1.179s) than on either VM (0.033s)**, inverting the entire premise of the native tier. Keys (always strings) are now hashed with FNV-1a into an open-addressed table probed linearly from the hash, with the cached hash compared before the key itself, deletion leaving a tombstone so probe chains stay intact, and tombstones counted toward the load factor so a churning map still grows. This is the structure ADR 014 (`docs/DECISIONS.md`) already specifies for Unfish maps — open addressing, linear probing, power-of-two capacities, 75% load factor, 32-bit FNV-1a for string keys — which the interpreter/VM map had always implemented and the native runtime had not. `hash_map_stress` went from 1.179s to **0.017s (~69x)** and `map_operations` from 0.097s to 0.009s (~11x); native is no longer slower than either VM on any of the 13 benchmarks (it had been the slowest tier on both map-heavy ones). Map semantics are unchanged — insertion-order iteration, `keys`/`values`, `has_key`, `delete`, re-insertion after delete, and stringification all still match the interpreter byte-for-byte.

- **README — `unfish fmt` Does Not Exist**: the CLI reference documented `unfish fmt [-w] <file>`, but the command is `unfish format` and the in-place flag is `-i`/`--in-place`; following the README produced `Error: Could not open file 'fmt'`. ## [1.1.0] - 2026-09-04

### Added
- **Multi-Module Native C99 Compiler (Milestone 25)**:
  - Recursive compile-time module discovery with automatic dependency resolution across `import` and `from ... import` statements.
  - Namespaced symbol generation (`uf_m_<name>_...`) for variables, functions, lambdas, and structs per module, preventing symbol collisions.
  - Module initializers (`uf_init_mod_<name>`) exporting variables, functions, and structs into runtime exports map.
  - Runtime module registry with `uf_register_module` / `uf_import_symbol` in `unfish_runtime.h`.
  - Circular import detection (`CircularImportError`) with `is_loading` guard in module registry.
  - Module search path resolution: caller directory → current directory → `src/stdlib/<name>.unfish` → `UNFISH_PATH`.
  - CLI `_with_path` API variants (`uf_emit_c_program_with_path`, `uf_build_native_with_path`).
  - Positional output argument support for `build` and `emit-c` commands (`unfish build foo.unfish output_binary`).
- **3-Way Differential Parity Testing**:
  - Extended `tools/run_differential_tests.sh` to verify AST Interpreter == Bytecode VM == Native C99 binary for all 44 positive conformance tests.
  - All 60 tests (44 positive + 16 negative) pass with 100% parity under ASan/UBSan.
- **Scientific/Exponent Notation Number Literals**: `1e10`, `6.022e23`, `1.5e-10`, `2.5E+3` now lex as a single number token (previously only plain decimal integers/floats were supported — `1e10` was a syntax error). The lexer speculatively consumes `e`/`E` + optional sign + digits and backs out if no digit follows, so `1e` immediately followed by an identifier still lexes as the number `1` followed by that identifier rather than erroring.
- New conformance tests: `36_large_map.unfish` (map resize stress), `37_closure_patterns.unfish` (closures, nested closures, spread patterns), `38_deep_closures.unfish` (multi-level transitive closure capture, closures over match-pattern bindings, mutable-capture chains), `39_closure_edge_cases.unfish` (per-iteration `for`-loop closures, recursive local closures with self-mutation, 4-level transitive capture with mutation, closures over struct-pattern fields), `40_cyclic_structures.unfish` (self- and mutually-referential arrays/maps/structs, plus equality on them), `41_json_cycle_detection.unfish` (json.stringify raises a catchable error on a cyclic structure), `42_scientific_notation.unfish`, `43_json_number_formatting.unfish`, and `44_builtin_name_shadowing.unfish` (a local variable/closure capture named after a builtin function).

### Fixed
- **Native C99 Codegen — Mutable Closure Captures**: Closures compiled to native C99 captured variables by value (a `memcpy` into the closure's environment struct at creation time), so a variable mutated from inside a closure (e.g. a `make_counter()`-style counter incrementing its own state on each call) would reset to its original value on every invocation instead of persisting, diverging from the AST interpreter and bytecode VM's shared-environment semantics.
  - Any variable captured by a closure is now heap-boxed (`UfVal*`, allocated via `uf_box_new`) and shared by reference between its defining scope and every closure invocation that captures it, so mutations are visible on subsequent calls and in the enclosing scope, matching interpreter/VM behavior. Boxing applies uniformly at every declaration site a captured name can originate from (`let`, function/lambda parameters, `for` loop variables, `try/catch` bindings, `match` pattern bindings, `import`/`from...import` bindings) and at every read/write site, so declaration and usage always agree on storage class.
  - Boxes are tracked in a dedicated list (`g_uf_rt.all_boxes`) and freed by `uf_cleanup()`, so the fix introduces no memory leaks (verified leak-free under AddressSanitizer/LeakSanitizer).
- **Native C99 Codegen — Transitive Closure Capture**: A closure nested two or more levels deep (e.g. `outer` → `middle` → `inner`, where `inner` reads a variable owned by `outer`) failed to compile (`'uf_var_x' undeclared`) because the intermediate closure (`middle`) never itself captured the name it needed to relay downward. Capture analysis now propagates captured names up through the closure nesting chain in a single reverse-dependency-order pass, so every closure in the chain captures and forwards whatever its descendants need.
- **Native C99 Codegen — `match`-Pattern Variable Capture**: A closure defined inside a `match` arm that reads the arm's pattern-bound variable (`when x if x > 0: function show(): ... x ...`) was misanalyzed as capturing an outer-scope variable named `x` rather than recognizing it as a binding local to the arm; when that arm's closure sat inside another closure (not a top-level function directly), this produced the same `'uf_var_x' undeclared` compile failure. Pattern-bound names (including nested struct-pattern fields) are now recorded as locals for capture analysis, matching how `let`, `for`, and `catch` bindings are already handled.
- **Native C99 Codegen — Stack Overflow on Compile**: `uf_emit_c_program_with_path` held its module-collection and main emission context (each holding up to 256 per-lambda capture-analysis records) as plain by-value local variables; combined with the fixed-size, 64-module module-collection array this comfortably exceeded a typical 8MB thread stack, crashing the compiler (`AddressSanitizer: stack-overflow`) on any program with closures, before it could emit a single line of output. These are now heap-allocated.

- **Runtime (Interpreter, VM, and Native C99) — Stack Overflow on Cyclic Structures**: Stringifying a value (`say`, `print`, `to_string`, the REPL's auto-printed result, `uf_val_repr`/`uf_val_to_string` in the shared runtime, and `uf_to_str` in the native runtime) recursed into array elements, map values, and struct fields with no cycle detection, so a self- or mutually-referential structure (`let m = {}; m["self"] = m`) recursed forever and crashed with a stack overflow — reproducible from ordinary user code, not just the REPL feature that surfaced it. All four stringification paths (interpreter/VM's `uf_val_to_string` and `uf_val_repr`, and the native runtime's `uf_to_str`) now track the container pointers currently being printed on the call chain and print `[...]`/`{...}`/`Name(...)` for a repeated container instead of recursing into it again, matching the convention Python's `repr()` uses for cycles. Verified leak-free under AddressSanitizer/LeakSanitizer and identical across all three execution backends.
- **Equality (`==`) on Cyclic Structures — Same Stack Overflow**: `uf_val_equal` (interpreter and VM, which share it) and the native runtime's `uf_eq_bool` compared array elements/map values/struct fields recursively with no cycle detection. `m == m` for a self-referential map was already accidentally safe in the interpreter (an existing same-pointer shortcut), but comparing two *distinct* structures that are each independently self-referential (`m1["self"] = m1; m2["self"] = m2; m1 == m2`) recursed forever in all three backends, and the native runtime didn't even have the same-pointer shortcut, so `m == m` crashed there too. Both now track the `(a, b)` pointer pairs currently being compared and treat a pair re-encountered mid-comparison as equal — the standard co-inductive convention Python's list/dict equality uses for cycles — so both the self-identity and distinct-cyclic-structures cases now terminate and agree across all three backends.
- **`json.stringify` — Same Cyclic-Structure Stack Overflow**: `json.stringify` (both the interpreter/VM's `stdlib/uf_mod_json.c` and the native runtime's `_json_stringify_val`) had the identical unbounded-recursion bug independently. Since JSON has no syntax for a cycle, it now raises a catchable `TypeError: Converting circular structure to JSON` instead (matching JS's `JSON.stringify` behavior) rather than printing a `"..."` placeholder that wouldn't parse back as valid JSON. Both stringifiers propagate a plain success/failure result up to their top-level caller before raising, rather than raising from inside the recursive descent, so the error's `setjmp`/`longjmp`-based unwind (when caught by a `try`/`catch`) can't skip past — and leak — the in-progress output buffer.
- **Native C99 Runtime — Garbled Output for Large Whole Numbers**: The native runtime's `uf_to_str` formatted any whole-valued number with `%.0f` unconditionally (`floor(n) == n`), unlike the interpreter/VM's equivalent which only does that below `1e15` and falls back to `%.14g` (scientific notation) above it. A value like `1.5e300` (a "whole number" at that magnitude, since every double past a certain size is) tried to print ~300 digits into a 128-byte stack buffer — not a memory-safety bug (`snprintf` is bounds-checked) but silently truncated, garbled output that disagreed with the interpreter/VM. Added the same `fabs(n) < 1e15` magnitude guard.
- **`json.stringify` — Undefined Behavior on Out-of-Range Numbers**: Both JSON stringifiers (interpreter/VM and native) tested whether a number was a whole number via `val == (double)(int64_t)val`, but converting a `double` outside `int64_t`'s range (or NaN/infinity, in the interpreter's case, which didn't filter those first) to `int64_t` is undefined behavior in C, not just wrong — it's not guaranteed to produce any particular value. Replaced with the same NaN/infinity/`fabs(n) < 1e15` guard as the other stringifiers, checked *before* the now-safe `int64_t` cast.
- **Native C99 Codegen — Local Variables Named After a Builtin**: A local variable or closure parameter sharing a name with any of the ~80 builtin functions (`log`, `min`, `max`, `sort`, `keys`, `filter`, `find`, ...) — an entirely ordinary, legal choice, and one the AST interpreter and bytecode VM already handled correctly via normal lexical shadowing — failed to compile in the native backend (`'uf_var_log' undeclared`) whenever a nested closure read it as a value, because capture analysis treated any name matching a builtin as always resolved to that builtin and never considered it capturable. Fixed by only skipping capture analysis for a builtin-matching name when it's the direct callee of a call (the one case where emit_expr genuinely always builtin-dispatches it, matching runtime behavior) — everywhere else, a builtin-shaped name is now analyzed like any other identifier. Known remaining gap: calling a variable that shadows a builtin *by that name* (`let log = fn ...; log(5)`) still dispatches to the builtin rather than the shadowing value in the native backend, unlike the interpreter/VM — the call-site fast path has no lexical-scope awareness to detect that narrower case. Reading such a variable as a plain value (not calling it) is unaffected and correct.

- **Bytecode VM — `continue` Inside a `for` Loop Was an Infinite Loop**: The bytecode compiler's `continue` unconditionally jumped straight back to the loop's condition-check point (`start_ip`). For `while` that's correct (the condition re-check *is* the right continue target), but `for`/`repeat` loops compile to a hidden index/counter that's advanced by code emitted *after* the loop body, right before the backward jump to `start_ip` — so jumping to `start_ip` directly skipped that advance entirely. In a `for` loop this meant the hidden index never changed once `continue` fired once, so the condition re-check saw the exact same loop variable value forever: `for i in range(5): if i % 2 != 0: continue` printed `0` and then hung indefinitely (100% CPU, no further output) — a simple, easily-written pattern, not an exotic one. In a `repeat N times:` loop it didn't hang (the hidden counter and any user-visible loop state are independent) but silently ran one extra iteration per `continue`, an off-by-one. Fixed by giving `continue` its own list of forward jumps per loop (mirroring how `break` already works), patched to land at the correct per-iteration "advance and re-check" point for each loop kind — the condition re-check for `while`, immediately before the hidden advance for `for`/`repeat`. The native C99 backend was never affected (it compiles loops to real C `for`/`while` with native `continue`, so C's own correct semantics applied already). Extended `tests/conformance/14_break_continue.unfish`, which — despite its name — had covered `continue` only inside `while`, never inside `for` or `repeat`, letting this through.

### Changed
- **Native C99 Codegen — Fixed-Capacity Limits Now Fail Loudly**: The emitter's internal bookkeeping (closures per program, captures per closure, local bindings per closure body, top-level functions/structs/variables per module) uses fixed-capacity arrays sized generously for ordinary programs. Previously, exceeding one silently dropped the overflow, which could produce a wrong-but-compiling binary (e.g. a closure the emitter lost track of silently became `uf_null()`) rather than a build error. Any overflow of these compiler-internal limits now fails the build with a specific, actionable error message instead; the AST interpreter and bytecode VM have no such limits and are unaffected.
